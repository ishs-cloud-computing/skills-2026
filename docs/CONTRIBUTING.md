# 문서 기여 가이드 (CONTRIBUTING)

이 저장소의 모든 문서는 아래 규칙을 지킨다. AI 초안이든 사람이 쓴 글이든 예외 없다.
규칙의 목적은 하나다 — **읽는 사람이 3초 안에 필요한 것을 찾게 한다.**

문서를 읽기 어렵게 만드는 가장 큰 원인은 문장력이 아니라 **종류를 섞는 것**이다.
그래서 이 가이드는 "종류 정하기"에서 시작한다.

---

## 1. 먼저 문서 종류를 정한다 (Diátaxis)

모든 문서는 아래 네 종류 중 **하나**에 속한다. 한 파일에 둘 이상을 섞지 않는다.
섞고 싶으면 파일을 나누고 링크로 연결한다.

| 종류 | 대상 독자 | 목적 | 우리 저장소 예시 |
|------|-----------|------|------------------|
| **Tutorial** | 처음 하는 사람 | 손잡고 끝까지 성공시킨다 | "EKS 클러스터 처음 띄우기" |
| **How-to / Runbook** | 할 줄 아는 사람 | 특정 작업을 완수시킨다 | "Karpenter NodePool 스케일 조정", "RDS failover 대응" |
| **Reference** | 값을 조회하는 사람 | 사실을 정확히 나열한다 | "Terraform 변수 목록", "ALB 리스너 규칙 표" |
| **Explanation** | 이해하려는 사람 | "왜 이렇게 했는가"를 설명한다 | "왜 Cluster Autoscaler 대신 Karpenter인가" |

### 종류별 철칙

- **Tutorial** — "왜"는 최소화한다. 무조건 성공하는 경로 하나만 제시한다. 갈림길·예외를 넣지 않는다.
- **How-to / Runbook** — 개념 설명을 넣지 않는다. 전제 조건 → 단계(명령문) → 검증 방법 순서로만 쓴다.
- **Reference** — 설명하지 않는다. 나열한다. 표·목록·스키마 위주. 서술형 문단을 넣지 않는다.
- **Explanation** — 배경, 트레이드오프, 결정 이유를 쓴다. 절차나 명령어를 넣지 않는다.

### 세트가 많을 때

세트마다 Tutorial을 새로 쓰지 않는다. 다음 구조를 따른다.

- **공통 개념(Explanation)** — 저장소에 한 번만 쓰고, 각 세트 문서에서 링크한다.
- **세트별 Runbook + Reference** — 세트마다 달라지는 건 단계와 값뿐이다. 이 둘만 세트별로 둔다.

## 2. 문장·구조 규칙

아래 규칙은 Google / Microsoft / Apple 개발자 문서 스타일 가이드가 실제로 강제하는 항목을 추린 것이다.
출처는 문서 맨 아래 레퍼런스 참고.

### 구조

- **결론 먼저 (BLUF, inverted pyramid).** 가장 중요한 정보를 문단 첫 문장에 둔다. 위에서부터 잘라도 말이 되게 쓴다.
- **조건 먼저, 지시 나중.** "노드가 부족하면 `kubectl scale`을 실행한다" (O) / "`kubectl scale`을 실행한다, 노드가 부족하면" (X). — Google 규칙
- **한 문단 = 한 아이디어.** 문단이 5줄을 넘으면 쪼갠다.
- **제목은 sentence case.** "Get started" (O) / "Get Started" (X). — Google 규칙

### 문장

- **2인칭 · 현재형 · 능동태.** "이 함수는 문자열을 반환한다" (O) / "문자열이 함수에 의해 반환된다" (X). — Google/MS/Apple 공통
- **명령형으로 절차를 쓴다.** "노드가 스케일될 수 있다" (X) → "`kubectl scale`로 스케일한다" (O).
- **적을수록 좋다 (bigger ideas, fewer words).** — Microsoft 규칙. 정보량 0인 문장을 삭제한다.
- **코드 요소엔 한정 명사를 붙인다.** `example.yaml` 단독으로 쓰지 않고 "the `example.yaml` file"처럼 쓴다. — Google 규칙
- **방향성 표현을 쓰지 않는다.** "아래 표", "위 명령어" 대신 대상을 직접 지칭한다. — Google 규칙

### 용어

- **한 개념 = 한 단어.** "노드 / 워커 / 인스턴스"를 섞지 않는다. 저장소 전체에서 하나로 고정한다. 용어가 흔들리면 신뢰가 깨진다. — Apple 규칙(용어 표준화)
- **소프트웨어를 의인화하지 않는다.** "Karpenter가 판단해서 알아서 해준다"류 표현을 피한다. — Apple 규칙
- **추상어를 구체값으로.** "성능이 향상된다" 금지. 실제 명령어 / 파일 경로 / 숫자(예: p99 200ms→40ms)로 쓴다.
- **ESL 독자 기준.** 관용구·농담·계절 비유를 넣지 않는다. 짧고 모호하지 않은 문장을 쓴다. — Google 규칙

## 3. 금지 목록 (AI slop 차단)

아래는 리뷰에서 무조건 반려한다. AI 초안에서 특히 자주 나온다.

- 섹션 끝마다 반복되는 요약 문장 ("정리하면…", "요약하자면…")
- "In conclusion", "결론적으로" 류의 닫는 문장
- 마케팅 형용사: powerful, seamless, robust, comprehensive, cutting-edge, leverage, utilize, 강력한, 손쉽게, 완벽하게
- 목 가다듬기 문장: "It's important to note that…", "오늘날처럼 빠르게 변하는…", "~하는 것이 중요합니다"
- "First… Second… Third…" 5문단 에세이 골격
- 수동태 절차 문장
- 25단어(한글 기준 약 45자)를 넘는 문장
- 검증 안 된 구체성(있어 보이는 가짜 숫자·가짜 인용)

## 4. AI로 초안을 만들 때

AI는 **originator(창작자)로는 약하고 reformatter(재정리자)로는 강하다.**
그러니 "왜"와 실제 값은 사람이 먹이고, 포맷만 AI에게 맡긴다.

### 순서

1. **문서 종류를 선언한다.** "이건 Runbook이다. 개념 설명 금지, 명령문 단계만."
2. **재료를 던진다.** 결정 이유, 실제 값, 제약, 장애 이력을 bullet로 준다. AI가 "왜"를 지어내지 않게 한다.
3. **금지 목록을 프롬프트에 박는다.** (아래 블록 재사용)
4. **좋은 예시 하나를 붙인다 (few-shot).** 기존의 잘 쓴 Runbook 하나를 프롬프트에 넣는다. 스타일 지시 열 줄보다 예시 하나가 더 잘 먹힌다.
5. **2패스로 돌린다.** 1패스: 초안. 2패스: "정보 없는 문장을 전부 삭제하고 30% 줄여라." — AI 초안은 길이 편향 때문에 항상 부풀어 있다.

### 재사용 프롬프트

```
이건 [Runbook / Reference / Tutorial / Explanation] 문서다.
아래 재료로만 작성하고, 없는 사실은 지어내지 마라.

[여기에 결정 이유·실제 값·제약·장애 이력을 bullet로]

규칙:
- 2인칭, 현재형, 능동태, 명령문 절차
- 결론 먼저, 조건 먼저 지시 나중
- 문장당 25단어 이하, 문단 5줄 이하
- 한 개념엔 한 단어만 사용

금지:
- 섹션 끝 요약, "결론적으로"류 마무리
- 마케팅 형용사(powerful/seamless/robust/leverage/강력한/손쉽게)
- "~하는 것이 중요합니다"류 군더더기
- 수동태, 5문단 에세이 골격
- 검증 안 된 숫자·인용

스타일 참고 예시:
[여기에 기존의 잘 쓴 문서 하나 붙여넣기]
```

**미검토 AI 출력을 그대로 merge하지 않는다.** AI 초안은 반드시 PR 리뷰를 거친다.

## 5. PR 리뷰 체크리스트

리뷰어는 아래를 확인하고 승인한다.

- [ ] 문서 종류가 하나로 명확한가? (Tutorial/How-to/Reference/Explanation을 안 섞었는가)
- [ ] 첫 문단에 핵심이 있는가? (BLUF)
- [ ] 절차가 명령문·능동태인가?
- [ ] "왜"가 필요한 곳에 실제 이유가 있는가? (AI가 못 채우는 부분)
- [ ] 추상어 대신 실제 명령어·값·숫자가 있는가?
- [ ] 금지 목록(3장)에 걸리는 표현이 없는가?
- [ ] 용어가 저장소 전체와 일관되는가?
- [ ] 실행 가능한 명령·코드가 실제로 동작하는가? (직접 실행 확인)

## 6. 파일 구조 · 네이밍

- 파일명은 kebab-case: `scale-karpenter-nodepool.md`
- 각 종류 폴더의 스켈레톤(`_templates/`)에서 시작한다. AI는 스켈레톤의 빈칸만 채운다.
- 세트 공통 Explanation은 한 곳에 두고 링크로 재사용한다.
